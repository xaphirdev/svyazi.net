
# svyazi.net — веб-отчётность на Go и MariaDB 10.1

Go обслуживает API и веб-интерфейс. MariaDB 10.1.48 работает на порте 3306 только во внутренней сети Docker. Порт базы не публикуется на виртуалке. Приложение использует пул соединений; SQLite и автоматического переключения на локальную БД больше нет.

Две базы на одном сервере:

- `svyazi_net_users`: персональные учётные записи, bcrypt-хеши паролей, регион, ТЦ и график дежурств, связанный с ID инженера.
- `svyazi_net_incidents`: аварии, исходные строки сводки, назначения инженеров, отчёты смен и база решений. Сохраняются 19 полей из ТЗ, нулевая дата для НВ, исходные исторические категории и расчёт длительности/простоя.

## Запуск на Linux семейства Debian, amd64

Скрипт определяет Debian, Ubuntu и производные (например Linux Mint, Pop!_OS, Kali, Devuan) по `ID` / `ID_LIKE` в `/etc/os-release`, с дополнительной проверкой `/etc/debian_version`. Фиксированной привязки к версии Debian нет. Нужны рабочие APT-репозитории, Docker-совместимое ядро и архитектура amd64: образ MariaDB 10.1.48 сохраняет это ограничение. Установка на каждом из перечисленных дистрибутивов отдельно не проверялась.

Скопировать весь проект на виртуалку, из его папки выполнить:

```bash
sudo sh start.sh
```

Скрипт написан для POSIX sh: Bash, массивы и pipefail для развёртывания не нужны. При запуске через `sh start.sh` файл сам исправляет CRLF до чтения основной части; служебные скрипты также переводятся в LF. В репозитории добавлены `.editorconfig` и `.gitattributes`, в готовом архиве все shell-файлы имеют LF.

Скрипт проверяет наличие Docker и Compose. После обновления индекса APT выбирает доступный Docker Engine (`docker.io` или `docker-ce`) и Compose (`docker-compose-plugin`, `docker-compose-v2` или `docker-compose`). Недостающие пакеты устанавливаются одним вызовом `apt-get install`, вместе с необходимыми `ca-certificates`, `curl`, `iptables`. Работающая установленная версия Docker не заменяется. Отсутствие пакетов в подключённых репозиториях выводится как понятная ошибка. Требования официального Docker к системам описаны для [Debian](https://docs.docker.com/engine/install/debian/) и [Ubuntu](https://docs.docker.com/engine/install/ubuntu/); скрипт использует пакеты подключённых репозиториев конкретного дистрибутива.

Скрипт создаёт `.env`, сохраняет существующие пароли MariaDB, сначала запускает и проверяет базу, затем собирает приложение и ждёт HTTP-проверку `/healthz`. Проверка приложения обращается к MariaDB, а не просто проверяет открытый порт. При ошибке выводятся статусы контейнеров и последние логи; данные и тома не удаляются. Go на виртуалке не требуется — приложение собирается в контейнере Debian Bookworm. После проверки приложения устанавливаются разрешающие правила INPUT / DOCKER-USER; активные UFW и firewalld также получают разрешения. Существующие настройки не сбрасываются. Служба `svyazi.net-firewall.service` восстанавливает правила при загрузке и перезапуске Docker. Открывается только APP_PORT (по умолчанию 8000); прежние разрешения проекта для 3306 удаляются. Внешний firewall и NAT гипервизора настраиваются отдельно.

Приложение: `http://IP_ВИРТУАЛКИ:8000`.

| Название учётки | Логин | Пароль по умолчанию |
| --- | --- | --- |
| Администратор | admin | admin |
| Дежурный | duty | duty-local |

Новое имя настройки пароля администратора в `.env`:

```dotenv
admin.svyazi.net=admin
```

Это имя настройки, а не домен приложения. `start.sh` удаляет старую строку `SVYAZI_NET_ADMIN_PASSWORD`, добавляет новое значение по умолчанию, если оно не задано, и передаёт его контейнеру через `.local/app.env` (имена с точками не используются как shell-переменные). При запуске Go напрямую `.env` читается автоматически. Перед ручным `docker compose up` нужно один раз выполнить `start.sh` для создания служебных файлов.

Обязательные учётки создаются и синхронизируются при каждом старте приложения, в том числе на существующем томе. Для `admin` применяется значение `admin.svyazi.net`, для `duty` — `duty-local`. В базе хранятся bcrypt-хеши. Общий `duty` имеет постоянные права дежурного. Персональные инженеры получают права дежурного только на период своей смены `[начало, окончание)`; права проверяются при каждом запросе, интерфейс обновляет роль раз в 15 секунд. Время графика — Екатеринбург, UTC+5.

### Начальные инженеры, график и решения

При первом запуске автоматически добавляются:

- 90 инженерных учёток: по пять для каждого из 18 ТЦ. Логины имеют вид `ekb.eng01`–`ekb.eng05`, `asb.eng01`–`asb.eng05` и т. д. У каждой учётки свой случайный пароль, регион и ТЦ. Названия «Инженер ЕКБ 01» — стартовые технические имена, не реальные ФИО.
- График на 30 суток для каждого ТЦ: 60 смен по 12 часов, 08:00–20:00 и 20:00–08:00 (Екатеринбург, UTC+5). Начало — текущая смена в момент первого запуска. Пять инженеров чередуются, каждому достаётся 12 смен; всего 1080 назначений. В интерфейсе есть фильтр по ТЦ.
- 36 ситуаций в базе знаний: питание, АКБ, ДГУ, охлаждение, GSM/LTE, RRU, антенны, синхронизация, оптика, VLAN, маршрутизация, мониторинг и повторные аварии. В каждой указаны симптомы, проверки, действия и проверка восстановления. Это типовые заготовки, которые нужно сверять с регламентом и моделью оборудования.

Инициализация выполняется транзакционно под блокировкой MariaDB. Версия записывается в `svyazi_net_incidents.bootstrap_data`. Повторный запуск не создаёт дубли и не восстанавливает вручную удалённые стартовые записи. При наличии запланированных смен ТЦ в выбранном периоде его существующий график сохраняется целиком. График не продлевается автоматически: дальнейшие смены планирует администратор.

Для запуска без стартовых инженеров, графика и решений задать `SEED_INITIAL_DATA=0` в `.env` **до первого запуска**. Это не удаляет уже созданные данные. Обязательные `admin` и `duty` создаются независимо от этого флага. Регионы стартовых ТЦ заданы в `server/starter.go`; при иной внутренней структуре компании их нужно уточнить перед развёртыванием.

### Файл пользователей и паролей

После успешного запуска в корне проекта создаётся `accounts-for-reviewers.tsv`: копия всех учёток приложения для проверяющих с правами 600. Посмотреть её можно командой `sudo cat accounts-for-reviewers.tsv`. Файл пересоздаётся после каждого успешного развёртывания, исключён из Git, Docker build и архива поставки.

После успешного развёртывания скрипт выводит путь:

```text
.local/credentials/users-passwords.tsv
```

Файл содержит роль, логин, имя и открытый пароль всех учёток приложения, обновляется при добавлении инженеров, хранится вне веб-каталога и исключён из Git и Docker build. Права файла — 600, каталога — 700; владелец в Linux — UID 65532 (пользователь контейнера), root также может читать его. Просмотр:

```bash
sudo cat .local/credentials/users-passwords.tsv
```

Для инженеров, созданных до включения экспорта или импортированных без открытого пароля, указывается «НЕИЗВЕСТЕН: учётка создана до включения экспорта». Восстановить их пароли из bcrypt невозможно. Файл не публикуется HTTP-сервером. Не удалять каталог credentials при пересоздании контейнеров, если нужно сохранить известные пароли инженеров.

В журнале и отчётности доступны фильтры по направлению, ТЦ, категории, типу сети и аварии, сортировка по дате и категориям 1–3. Выгрузка CSV/XLSX содержит весь выбранный период, фильтры таблицы её не ограничивают.

Диагностика (если установлен Compose v1, использовать `docker-compose` вместо `docker compose`):

```bash
sudo docker compose ps
sudo docker compose logs --tail=100 db app
sudo systemctl status svyazi.net-firewall
```

Команда `systemctl` относится к системам с systemd. На SysVinit правила можно повторно применить через `sudo service svyazi.net-firewall restart`, на OpenRC — через `sudo rc-service svyazi.net-firewall restart`. Менеджер служб при развёртывании выбирается автоматически. Если менеджера служб нет, требуется уже работающий Docker; правила firewall применяются для текущего запуска без настройки автозагрузки.

## Обновление существующей Docker-установки

При обновлении уже работающей Docker-установки сначала сделайте резервную копию и остановите прежний контейнер приложения. Обновляйте файлы **в той же папке проекта**, сохранив `.env`, `.local/credentials` и имя проекта Compose: иначе Compose может выбрать другой том БД.

`start.sh` повторно настраивает базы `svyazi_net_users` и `svyazi_net_incidents`, а также SQL-пользователя `svyazi_net` на существующем томе. Скрипт `scripts/migrate-databases.sh` находит прежние базы по структуре таблиц и переносит таблицы вместе с ID, хешами паролей и графиком. Имена прежних баз не зашиты в код. Если найдено несколько источников или целевая таблица уже существует, перенос прекращается без перезаписи. Пустые исходные схемы и прежние SQL-пользователи автоматически не удаляются. Перенос идёт до запуска приложения и заполнения стартовых данных.

## Доступ к базе

MariaDB подключена только к внутренней сети Docker `database` (`internal: true`). У контейнера базы нет публикации портов на хосте; приложение подключается к `db:3306`. Внешний доступ к SQL-порту закрыт. phpMyAdmin, Adminer и другие веб-панели базы в проекте отсутствуют. Пароли, настройки и SQL-файлы HTTP-сервер не публикует; API приложения требует входа и проверяет роль.

Административный доступ с виртуалки:

```bash
sudo docker compose exec db mysql -uroot -p
```

Введите `DB_ROOT_PASSWORD` из `.env`. Для резервного копирования также используйте `docker compose exec`, не открывая порт базы.

## Карточки решений

В базе решений инженер указывает станцию и дату/время выполненного ремонта (Екатеринбург, UTC+5). Имя и ID инженера берутся из сессии, дата публикации сохраняется отдельно. В карточке показаны автор, ТЦ, станция, время ремонта и публикации. Для типовых инструкций и старых записей отсутствующие сведения обозначаются явно; история ремонтов для них не выдумывается. При обновлении нужные столбцы добавляются в существующую таблицу автоматически.

## Проверка сборки

Необязательные файлы тестов, импорта SQLite/Excel и упаковки архива удалены. Для запуска оставлены только необходимые скрипты развёртывания и миграции баз.

```bash
go build ./...
go vet ./...
node --check app.js
sh -n start.sh
```
